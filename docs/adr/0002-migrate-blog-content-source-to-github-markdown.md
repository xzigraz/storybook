# 2. Migrate blog content source from headless WordPress to GitHub-hosted markdown

## Status

Accepted

## Context

The blog (`app/blogs/page.tsx`, `app/blogs/[slug]/page.tsx`) currently sources content
from a headless WordPress instance over GraphQL (`WORDPRESS_GRAPHQL_URL`), proxied
through this app's own `/api/get-posts` and `/api/get-post` routes. That WordPress
instance runs on free hosting, which has not proven reliable — the actual motivation
for this change, not a technical dissatisfaction with GraphQL or WordPress as such.

Alternatives considered for a replacement content source:
- A GitHub repo accessed via the REST Contents API — structured JSON, built-in
  directory listing, supports auth for a much higher rate limit. Rejected in favor of
  the simpler option below, since a low-traffic personal blog doesn't need the higher
  rate limit or the listing endpoint badly enough to justify the extra response
  shape/auth complexity.
- A git submodule (mirroring the existing `ui-component` pattern) — rejected because
  it ties content updates to a rebuild/redeploy of this repo, and content is meant to
  be editable/publishable independently of the site's own release cycle.
- MDX via `next-mdx-remote` — rejected for now; plain markdown covers the current
  posts, and MDX's ability to embed live React components isn't needed yet. Revisit
  if a post ever needs that.

## Decision

Move blog content to a **new, dedicated, public GitHub repository** containing
markdown post files, fetched via **raw.githubusercontent.com** (no GitHub API, no
auth token — public repo means unauthenticated raw fetches work fine and get GitHub's
CDN caching for free).

Because raw.githubusercontent.com has no directory-listing endpoint, the content repo
also commits a **`posts.json` manifest** at its root (slug/title/date/excerpt per
post) — fetched the same way, then each post's full markdown body is fetched
separately by slug. The manifest is hand-maintained (not generated by a repo Action)
for now; simplest path, revisit if "forgot to update the manifest" becomes a recurring
problem.

Markdown is converted to HTML via a **remark/rehype pipeline** at request time, kept
close to the current `dangerouslySetInnerHTML` rendering shape in
`blogs/[slug]/page.tsx` (WordPress already returns pre-rendered HTML the same way) —
so the page components change what they fetch and how it's parsed, but not the
fundamental rendering approach.

The existing **`/api/get-posts` / `/api/get-post` indirection is kept**, repointed at
GitHub instead of WordPress, rather than fetching raw.githubusercontent.com directly
from the Server Components — even though the original reason for that indirection
(keeping a secret off the client) no longer applies to an unauthenticated public
fetch. Kept for consistency with the rest of the codebase's pattern and to preserve a
seam if server-side logic (caching, auth, format translation) needs to live there
later.

Repo visibility is **public**. Blog posts aren't sensitive; publishing a draft early
is an acceptable risk, mitigated by simply not committing a post until it's ready
(or keeping unpublished drafts out of `posts.json`).

## Consequences

- New env var(s) needed to point at the content repo (owner/repo/ref), replacing
  `WORDPRESS_GRAPHQL_URL`. `SERVER_BASE_URL` stays, since the internal API-route
  indirection is preserved.
- Publishing a new post becomes "commit a markdown file + update `posts.json` in the
  content repo" instead of "publish in the WordPress admin" — a workflow change to
  actually use, not just a backend swap.
- No more dependency on the free WordPress host's uptime; new dependency on GitHub's
  (and specifically raw.githubusercontent.com's) uptime and unauthenticated rate
  limits instead. Considered an acceptable trade for this site's traffic level.
- Losing WordPress means losing whatever WYSIWYG editing convenience it offered;
  posts are now authored as raw markdown files. Acceptable given posts are
  developer-authored already.
- If `posts.json` is ever forgotten on a new post, that post silently won't appear in
  the listing (fails silently, not loudly) — a known sharp edge of the hand-maintained
  manifest choice, not yet mitigated.
